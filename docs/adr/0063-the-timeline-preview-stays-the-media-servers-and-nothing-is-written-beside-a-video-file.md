# The timeline preview stays the media server's, and nothing is written beside a Video File

[ADR 0061](0061-a-user-preview-belongs-to-one-file-and-is-served-only-while-prdb-still-shows-it.md)
settled what may be asked of prdb about a user preview and deliberately left one
thing undecided:

> **The media-server output format.** Whether a sprite and a WebVTT beside a
> Video File are discovered and played by Jellyfin is a question about Jellyfin,
> and the answer is not predetermined. Until it is proven, no Library
> integration is chosen and none is counted as delivered.

It was put to a running Jellyfin 10.11.11 rather than reasoned about. The answer
is no — and the control run, which existed only to establish what a correct
import looks like, answers a larger question than the one that was asked.

**Nothing is written into the library. The timeline preview is the media
server's, and this decision closes the question rather than deferring it.**

The whole run, with the configuration, the readings and a recipe that reproduces
it, is in
[`docs/media-server-timeline-previews.md`](../media-server-timeline-previews.md).
What follows is only the argument.

## The import branch replaces, it does not add

`TrickplayManager.RefreshTrickplayDataAsync` takes its *import existing trickplay
tiles* branch where the directory exists, is not being replaced, and holds files.
It does not merge, it does not compare, and the server's own extraction never
runs for that file afterwards. A directory that is there **is** the answer.

So the choice was never *a timeline preview or none*. It is *ours or the
server's*, and the server's is better, from the same video:

| | generated by the server | imported from our pair |
| --- | --- | --- |
| Tiles | 12 | 1 |
| Sheet | 3200x1800 | 1280x540 |
| Playlist says | `320x180`, 120 s | `320x54`, 10 s |

The second row is not a near miss. A client crops `320x54` cells out of an
assumed `10x10` grid over an image that is four columns of 180-pixel tiles, and
is told the strip covers ten seconds of a two-minute film: every thumbnail it
draws is a horizontal third of the wrong picture, at the wrong time.

Three facts under that, read out of the source and then confirmed against the
server: nothing on disk carries the timing, because there is no manifest and the
WebVTT is never opened; the grid comes from server-wide settings rather than from
the image; and `ThumbnailCount` counts tile *files*, so one sheet is one
thumbnail.

## A correct re-cut is still the wrong trade

The supported path is real, and it is not what ADR 0061 imagined. It is not
publishing what prdb gave us; it is **re-cutting** prdb's sheet into the server's
grid at the server's uniform interval. Even done perfectly it loses:

- **Fidelity, in every case.** prdb's tiles are whatever resolution prdb
  published; the server's come out of the source file at its own
  `WidthResolutions`. Substituting the first for the second is a downgrade that
  no configuration makes good.
- **Time, not just resolution.** prdb's previews carry their own spacing — a
  hundred tiles across a twenty-two minute scene is 13.2 seconds a tile — and
  the server has one interval for the whole library. Fitting one to the other
  means resampling: some tiles shown twice, some never.
- **Consistency.** A user preview exists for some files and not others, so the
  result is a library where some entries scrub from our tiles and the rest from
  the server's, with no way for anybody to tell which.

What is gained is extraction time on the media server's machine. That is a real
cost for somebody with a large library on weak hardware, and it is not ours to
trade a correct picture for — least of all silently, in a tool whose own
`VISION.md` says the library it produces should be a media server's library
*directly*.

Binding the preview to the individual file — the thing the OS hash was carried
for — is free on the server's side, for a reason that cannot be competed with:
the server reads the file.

## Reading the server's settings is a different tool

The re-cut would be correct rather than assumed if this tool could read
`Interval`, `WidthResolutions`, `TileWidth` and `TileHeight` from the server.
That is ruled out a level above an ADR. `VISION.md` says:

> Not a media server or a player, **and not on the way to becoming one**. It
> produces a library; Jellyfin serves it.

A connection to a media server's API is a step onto exactly that path, and the
return on it would be a reimplementation of a feature the server already has.
Writing into a server's private data directory — which is the only way into Plex,
whose preview thumbnails are BIF files inside its own store — is refused for the
same reason and one more: it is a private store with its own identifiers and no
contract.

## The naive sidecar is worse than doing nothing

The other reading of *sidecar* — the pair beside the video, named after it, the
way `movie.nfo` and `fanart.jpg` are — was tested at the same time. The sheet was
ignored. **The WebVTT became an external subtitle track.**

That is not an unsupported feature quietly doing nothing. It is a visible defect
introduced into something that works today: a bogus entry in the subtitle menu of
every client, on every file this tool filed. It rules the layout out on its own,
before any question of fidelity.

## Considered options

**Re-cut at the server's default settings.** Rejected. Its stated cost was that
it is wrong for anybody who changed three settings — but the section above makes
it quietly worse for everybody, because it displaces a better preview rather than
supplying a missing one. An option whose best case is a downgrade is not a
trade-off.

**Read the server's trickplay configuration.** Rejected against `VISION.md`'s
non-goal, not against effort. It is the technically correct answer to the wrong
question.

**Leave the scope open.** Rejected. An investigation that came back negative is
an answer, and carrying an unimplementable intention forward would have every
later reader re-derive this run. The decision belongs written down, with the
measurements next to it.

## Consequences

- **ADR 0027 is unamended.** It is amended only for a demonstrated path, and what
  was demonstrated is that the intended one does not exist. `movie.nfo` and
  `fanart.jpg` are untouched, and the fixed list of what Filing writes beside a
  Video File does not grow.
- **ADR 0061 loses its third table.** `library_preview_asset` was to be the one
  exported row of that decision — an ownership record for a file written into the
  user's library. Nothing is written there, so nothing is owned there, and the
  table is not created. The export boundary is unchanged: both remaining tables
  are disposable, and ADR 0033's rule that every table declares its side is
  satisfied by the two that exist.
- **`CONTEXT.md`'s *Timeline Preview* changes meaning.** It stays in the
  glossary, and it now names something this tool does **not** own — which is the
  point of keeping it: a term that marks a boundary stops the boundary being
  crossed again by somebody who never saw this run.
- **A filed file still registers interest in its Video's previews**, and the
  interest still never expires — for a different reason than ADR 0061 gave. The
  reason is no longer a Library asset to reconcile; it is that those bindings are
  ADR 0062's evidence, and a withdrawal has to reach them for as long as the file
  is on disk.
- **The user previews keep the surfaces they have.** A Video's Preview and the
  Review Queue, where they are something a media server cannot offer: pictures of
  *this* file, and a hash that names it without anybody looking.
- **The documentation says where the checkbox is.**
  [`docs/running-in-docker.md`](../running-in-docker.md) points at the server's
  own per-library trickplay setting, so the outcome is reachable even though this
  tool does not produce it.
- **Nothing is reported upstream.** `ThumbnailCount` counting files rather than
  thumbnails is a defect on Jellyfin's own terms, and saying so is a separate act
  this project is not taking.
